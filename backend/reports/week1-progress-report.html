Complete System Overview - How Everything Works

Dispotree is a real estate deal management platform that automates the entire lifecycle of property deals from ingestion through offer acceptance. The system is built on a modular plugin architecture that allows each component to work independently while communicating through a central event system.

The Big Picture

At its core, Dispotree solves a specific problem: How do you efficiently match incoming property deals with hedge fund investors who have specific buying criteria?

The answer involves several interconnected systems:

  1. Deal Ingestion - Getting property data into the system from multiple sources
  2. Intelligent Scoring - Automatically evaluating each property against fund requirements
  3. Automation Engine - Taking action based on scores and events
  4. Marketplace - Presenting matched deals to the right buyers
  5. Transaction Management - Handling offers and contract signing

1. Deal Ingestion System - How Properties Enter the Platform

The first challenge is getting property data into the system. Different sources provide data in different formats, so we built a plugin-based ingestion system that normalizes everything into a standard format.

How Each Source Works:

CSV Upload Plugin

What it does: Accepts bulk property uploads via CSV files.

How it works:

  1. User uploads a CSV file through the POST /api/plugins/sources/csv endpoint
  2. System validates the file format and required columns (address, city, state, zip, asking price)
  3. Each row is parsed and mapped to the standard Property schema
  4. Properties are created in the database with source: 'csv' tag
  5. For each property, a deal.created event is emitted to trigger automations

Use case: Wholesalers who have spreadsheets of properties from their marketing campaigns.

API Push Plugin

What it does: Accepts real-time property submissions via REST API.

How it works:

  1. External system calls POST /api/plugins/sources/api with property JSON
  2. Request is validated against the Property schema using Joi validation
  3. Property is created with source: 'api' tag
  4. deal.created event fires, triggering scoring and automations

Use case: Integration with CRMs, lead generation tools, or partner systems.

Email Parser Plugin

What it does: Monitors an email inbox and extracts property data from incoming emails.

How it works:

  1. Connects to configured IMAP server (Gmail, Outlook, etc.)
  2. Polls for new emails matching configured criteria (sender, subject patterns)
  3. Parses email body and attachments using AI to extract property details
  4. Creates property records with source: 'email'
  5. Marks email as processed to avoid duplicates

Use case: Receiving deals from bird dogs or scouts who send leads via email.

Webhook Receiver Plugin

What it does: Accepts incoming webhooks from external platforms.

How it works:

  1. Exposes endpoint POST /api/plugins/sources/webhook/:sourceId
  2. Validates webhook signature (if configured) for security
  3. Maps incoming payload to Property schema using configurable field mappings
  4. Creates property with source: 'webhook'

Use case: Zapier integrations, PropStream exports, or custom integrations.

Firecrawl Web Scraper Plugin

What it does: Scrapes property listings from auction sites and listing platforms.

How it works:

  1. Uses Firecrawl API to navigate to configured URLs
  2. Extracts property data using CSS selectors or AI extraction
  3. Handles pagination to scrape multiple listings
  4. Deduplicates against existing properties by address
  5. Creates new properties with source: 'firecrawl'

Use case: Monitoring auction.com, Hubzu, or county tax sale sites.

3. Buy Box Scoring Engine

Once a property enters the system, it needs to be evaluated against each hedge fund's investment criteria. This is where the Buy Box Scoring Engine comes in.

What is a Buy Box?

A "Buy Box" defines a hedge fund's ideal investment property. It includes criteria like:

  • Geographic focus (specific states, cities, or zip codes)
  • Property type (Single Family, Duplex, Multifamily)
  • Price range (min/max asking price)
  • Equity requirements (minimum equity percentage)
  • Property condition (year built, square footage)
  • ARV thresholds (After Repair Value requirements)

How Scoring Works:

Step 1: Criteria Definition

Each fund defines their buy box with weighted criteria. For example:

  • State must be TX, FL, AZ, or GA (weight: 20 points)
  • Property type must be Single Family (weight: 15 points)
  • Asking price between $100K-$350K (weight: 25 points)
  • Equity percentage >= 20% (weight: 25 points)
  • Year built >= 1980 (weight: 15 points)

Step 2: Automatic Scoring

When a property is created, the system automatically:

  1. Loads all active buy boxes from the database
  2. Evaluates the property against each buy box's criteria
  3. For each matching criterion, adds its weight to the score
  4. Calculates final score as percentage (0-100)
  5. Stores all scores in the property record

Step 3: Score Storage and Events

After scoring completes:

  • All fund scores are stored in the buyBoxScores JSON field
  • The highest score is stored in topScore for quick filtering
  • The best-matching fund ID is stored in topFundId
  • A score.calculated event fires with all score data
Example: A property in Texas, Single Family, asking $250K, with 25% equity, built in 1995 would score:
  • State match: +20 points
  • Property type match: +15 points
  • Price in range: +25 points
  • Equity >= 20%: +25 points
  • Year built >= 1980: +15 points
  • Total: 100/100 (perfect match)

5. Multi-Step Workflow System

While automations handle simple trigger-action patterns, workflows orchestrate complex multi-step processes that may span days or weeks.

How Workflows Differ from Automations:

Feature Automation Workflow
Steps Single action or parallel actions Multiple sequential/parallel steps
State Stateless (fire and forget) Stateful (persisted to database)
Duration Milliseconds Hours, days, or weeks
Waiting No waiting capability Can wait for events or timeouts
Branching No conditional branching If/else logic between steps

Workflow Execution Process:

Step 1: Workflow Initiation

A workflow starts when:

  • An automation's startWorkflow action fires
  • A user manually triggers it via API
  • Another workflow step triggers it

The system creates a WorkflowExecution record with status "running" and current step = 1.

Step 2: Step Execution

For each step, the workflow engine:

  1. Loads the step configuration (action type, parameters)
  2. Executes the step's action (notify, create task, call API, etc.)
  3. Checks if step has a wait condition
  4. If no wait, immediately moves to next step
  5. If wait required, pauses and stores state to database

Step 3: Wait Conditions

Workflows can pause and wait for:

  • Event: Wait until specific event fires (e.g., document.uploaded)
  • Timeout: Wait for specified duration (e.g., 48 hours)
  • Approval: Wait for user to approve/reject
  • External: Wait for webhook callback

While waiting, the workflow state is persisted to PostgreSQL, so it survives server restarts.

Step 4: Conditional Branching

Steps can specify different next steps based on conditions:

  • If ROI > 15%, go to "Generate Offer" step
  • Else, go to "Reject Deal" step

This allows complex decision trees within a single workflow.

Step 5: Completion

When the final step completes:

  • Workflow status set to "completed"
  • Completion timestamp recorded
  • workflow.completed event emitted
  • Audit log finalized with all step results

6. ML Prediction System - AI-Powered Deal Scoring

Beyond rule-based buy box scoring, the ML system learns from historical data to predict deal quality and fund preferences.

How the ML Pipeline Works:

Training Data Collection

The system collects training data from:

  • Fund Feedback: When funds accept/reject deals, feedback is recorded
  • Offer Outcomes: Which offers get accepted vs rejected
  • User Behavior: Which deals get views, likes, and offers
  • Deal Velocity: How quickly deals move through the pipeline

Each data point is stored in the FundFeedback model with the property features and outcome.

Model Training

Using TensorFlow.js, the system trains neural network models:

  1. Collects all feedback data from database
  2. Extracts features: price, equity, location, property type, etc.
  3. Normalizes features to 0-1 scale
  4. Trains model to predict: Will this deal be accepted?
  5. Saves model weights to ModelVersion table
  6. Records training metrics in TrainingRun

Prediction Generation

When new deals enter the system:

  1. Property features are extracted
  2. Features normalized using same scalers as training
  3. Model generates prediction score (0-1 probability)
  4. Score stored in MLPrediction table
  5. Prediction linked to property for analytics

Model Versioning and A/B Testing

The system supports multiple model versions:

  • Each model version tracked with accuracy metrics
  • Can run A/B tests between model versions
  • Automatic rollback if new model underperforms
  • Predictions logged with model version for analysis

8. Contract Signing System

The contract system handles the complete document lifecycle from template creation through multi-party signing.

How Contract Signing Works:

Template Management

Contracts start as reusable templates:

  • Templates stored with placeholder variables like {{buyerName}}, {{propertyAddress}}
  • Support for multiple template versions
  • Templates organized by type: Purchase Agreement, Assignment, etc.
  • Admin interface to create and edit templates

Contract Generation

When a contract is needed:

  1. System loads the appropriate template
  2. Pulls data from Property, User, and Offer records
  3. Replaces all placeholders with actual values
  4. Generates PDF preview
  5. Creates Contract record with status "pending_signatures"

Signature Collection

Multi-party signing process:

  1. System identifies required signers (buyer, seller, agent)
  2. Sends signing requests via email with secure links
  3. Each signer accesses contract through unique token
  4. Captures signature (typed name or drawn signature)
  5. Records timestamp, IP address, and user agent
  6. Updates contract status as signatures are collected

Completion and Storage

When all parties have signed:

  • Final PDF generated with all signatures embedded
  • Contract status updated to "executed"
  • All parties receive copy via email
  • Document linked to property record
  • Complete audit trail available for compliance

11. Security and Authentication

JWT Authentication Flow:

Login Process

  1. User submits email + password to POST /api/auth/login
  2. System verifies password against bcrypt hash (12 rounds)
  3. If valid, generates access token (15 min expiry) and refresh token (7 day expiry)
  4. Tokens returned to client for storage

Request Authentication

  1. Client includes access token in Authorization header
  2. authenticate middleware validates token signature
  3. Checks token expiration
  4. Attaches user object to request for downstream use

Token Refresh

  1. When access token expires, client calls POST /api/auth/refresh
  2. Includes refresh token in request body
  3. System validates refresh token and issues new access token
  4. No password required for refresh

Rate Limiting:

Endpoint Limit Window
Login/Register 10 attempts 15 minutes
Password Change 5 attempts 1 hour
General API 100 requests 1 minute

AI & Machine Learning Services

OpenAI GPT-4
Large Language Model
Why: Powers the conversational AI agent for natural language property searches, deal analysis, and automated insights. GPT-4 provides the reasoning capability to understand complex queries like "find me deals in Texas with 20% equity under $300K" and translate them into database operations.
LangChain
AI Orchestration Framework
Why: Provides the agent framework that connects GPT-4 to our 20+ tools. Handles conversation memory, tool selection, and multi-step reasoning. Enables the AI to chain together multiple operations (search → score → analyze → recommend).
Pinecone
Vector Database
Why: Stores document embeddings for semantic search in the knowledge base. When users ask questions, Pinecone finds the most relevant documents by meaning (not just keywords). Essential for RAG (Retrieval Augmented Generation).
TensorFlow.js
ML Runtime
Why: Runs neural network models directly in Node.js for deal quality prediction. No external API calls needed for ML inference, reducing latency. Trains custom models on fund feedback data to predict which deals will get accepted.

Database & Storage

Why: Robust, ACID-compliant database for transactional data. Supports JSON columns for flexible schema (buy box criteria, workflow state). Excellent for complex queries needed for analytics and reporting.
